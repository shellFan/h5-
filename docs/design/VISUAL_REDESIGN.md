# 膨胀小队 · UI 与游戏美术改版设计书

日期：2026-11-21。状态：设计方案，待关键视觉稿确认后分批制作。范围：视觉设计和资产规范。

## 1. 现状与设计依据

项目是竖屏 3D 小队射击 H5，Three.js 本地版本实际为 **r149**。已有蓝色士兵、城市道路、状态门、僵尸与 Boss GLB、八类武器、本地真实战绩榜和基础弹道/粒子。

依据包括 `js/config.js`、`js/weapons.js`、`js/leaderboard.js`、现有截图和 V50 美术/UI 文档。历史文档中的关卡对应表部分已经过期，本方案以当前配置为准。例如当前第 6 关是末日核心与 overlord Boss，不采用旧模型目录中的“双生精英第 6 关”描述。

现有美术文档说明了刚体五部件模型及实例化方式。这些是交付约束，不能把普通立绘当成可直接使用的怪物模型，也不能在没有接入验证时宣称完成了游戏内改版。

## 2. 风格方向

推荐方向：**明亮卡通军事 + 轻废土 + 清晰的玩具模型质感**。

选择理由：与现有蓝色小队、夸张僵尸和竖屏跑道兼容；远景和敌群在手机上易读；可分批替换，不必推翻全部资产。

另两种方向作为比较：暗黑写实末日适合氛围，但会压低远处怪物和门的可读性；全套霓虹科幻能突出特效，但与现有城市和士兵差异大，重制范围更广。当前采用前述推荐方向。

### 2.1 形体、材质、光线

- 友方：圆润头盔、紧凑装备、稳定直立轮廓；蓝色为核心身份色。
- 普通敌人：不对称肩线、前倾躯干、突出头部/手部；不同怪物用轮廓区分，不只换色。
- Boss：一个清晰的主特征，例如大盾、巢囊、机械拳；其他装饰保持次要。
- 环境：大色块、低频材质细节，纹理密度低于角色；路面与敌人脚部保持明度差。
- 金属呈柔和亮边，布料哑光，皮肤不做镜面塑料高光；不追求写实污渍。
- 主光方向和材质明暗保持一致；暗色关卡用局部补光保住敌人轮廓，不把整片画面染成同色。

### 2.2 色彩职责

| 职责 | 建议色 | 视觉用途 |
|---|---|---|
| 主面板 | `#14253D` | 深蓝操作面板、信息底板 |
| 主文字 | `#E8F0F8` | 面板标题和数值 |
| 次文字 | `#9BAEC4` | 描述、日期和辅助标签 |
| 友方蓝 | `#3B82F6` | 小队身份、已选状态、装备部件 |
| 主操作/奖励金 | `#FFC85A` | 开始战斗、领奖、前三名；按钮文字用深蓝 |
| 补员绿 | `#39D98A` | 补兵通知、治疗光圈 |
| 危险红 | `#F06464` | 敌方攻击预警与战损；同时配图形/文字 |
| 技能紫 | `#A888FF` | 技能和稀有信息 |
| 冰冻青 | `#71DDF5` | 冰冻武器、结晶命中 |

色值是设计目标，需在现有 r149 管线的游戏截图中校色。文字对比度以正常文字至少 4.5:1 为目标。怪物、奖励和危险不能仅靠颜色辨识。

## 3. UI 设计系统

### 3.1 尺寸与适配

- 主设计稿：390×844，单位为界面逻辑像素，截图/导出需注明倍率。
- 必查尺寸：360×640、390×844、430×932、768×1024；短屏保持主要按钮可见，列表滚动。
- 安全区外留给背景，关键文本和按钮在设备安全区内。主内容横向内边距 16，模块间距 12/16/24。
- 正文 14–16，主数值 24–32，主标题 28–32；辅助文字不承担唯一的关键说明。
- 主要触控区域不小于 44×44；图标可以较小，但需标出完整热区。
- 按钮圆角 14、卡片 18、弹层 24。统一实体圆角图标风格，逐步替代混用的系统 emoji。
- 按钮必须包含普通、按下、已选、禁用状态；按下演出目标 100–140ms，不阻塞操作。

### 3.2 文字与层级

第一层：关卡目标、选择门内容、Boss 预警、人数变化。第二层：当前人数、武器和战斗进度。第三层：连杀、货币和装饰。

视觉层级遇到冲突时，优先让玩家读清怪物动作和门的选项；减少同时展示的装饰。长中文、四位数以上数值和双行通知必须给出样例。

## 4. 逐页视觉方案

### 4.1 首页

- 顶部：游戏标志、小队徽章、当前资源；资源图标各有稳定位置。
- 主视觉：蓝色小队围绕代表性枪械形成三角构图，背景沿用当前城市主题。
- 当前关卡卡片：关卡名、场景缩略图、现有解锁状态与简短目标。
- 主按钮“开始战斗”使用金色，宽度占主内容区，视觉权重高于其他入口。
- 军械库、成长、挑战、战绩等现有入口用统一按钮家族。入口数量和跳转关系沿用现有功能，不新增奖励页或付费入口。

交付：首页完整稿、关卡卡片三态、资源胶囊、主按钮四态。

### 4.2 战斗 HUD 与选择门

- 顶部进度条控制在约 72 高的信息带内；头像、关卡名、暂停按钮保持稳定，不随通知移动。
- 左侧紧凑属性条显示现有的人数、输出和射速，减少厚边框/高光对视野的占用。
- 390×844 稿中约 y=130–220 预留通知区；遇 Boss 血条/预警时需要画出避让版本，接入时按安全区调整，不将该坐标当成所有设备固定值。
- 中部约 30%–68% 高度为敌群与选择门主要阅读区，避免大幅横向遮罩。底部保留拖动操作视野，广告刷门按钮仍需与拖动区域区分。
- 门框沿用跑道宽度；用小队、子弹、技能符号辅助识别。门收益文字始终高于玻璃装饰，稀有度有角标/边框形态，不单靠颜色。
- 不新增门、不调整门触发规则；开放、未开放和获得后的外观仅反映程序已有状态。

**补兵反馈延续上一轮已接入的信息规则：**显示“来源 + 实际增加人数”，例如“空投补给 +15人”“战地医疗 +2人”。同来源高频增长合并，绿色足底光圈和上升粒子作为辅助；不得用“+15”误报实际只补了 1 人的情况。

交付：普通战斗、选门、Boss 战、补兵/战损同时发生四张状态稿；三类门的正面图和标签样式。

### 4.3 军械库/枪械详情

- 上部展示武器外观，下面依次为名称、现有等级/进化状态、现有属性描述和操作按钮。
- 八类武器采用同一相机方向、同一画幅占比与光线；装备中的武器有实心徽章，锁定武器有锁图形和解锁条件文字。
- 升级视觉体现部件变化：弹匣、枪托、瞄具、能量组件。进化增加可识别的结构特征，不给所有武器套一圈相同金光。
- 不修改攻击参数、解锁门槛、升级消耗和进化条件；没有数据的属性不在视觉稿中虚构。

### 4.4 排行榜/战绩页

当前 H5 数据来源是本机真实对局记录，最多 20 条，并非联网全球玩家排名。推荐标题“本机战绩榜”，副标题“仅记录此设备上的真实对局”。同一玩家的不同对局不能伪装成不同真人。

- 顶部前三名：金、银、铜奖牌与 1/2/3 数字，重点突出分数；记录不足三条时自然收缩，不补假名字/假分数。
- 其余行：名次、职业徽章、分数；第二行显示关卡、胜负和日期。展开/详情稿可排列击杀、最高人数、连杀、用时等已有字段。
- 设计宽度 390 下，列表行高度目标 76–88，最长关卡名允许两行；数字列右对齐。
- 空状态：“还没有战绩，完成一局后会记录在这里”；离线本地榜不显示虚假的加载失败或登录门槛。
- 若后续接入真实平台榜，再由程序方提供对应数据和授权状态；当前不摆出“全球榜/好友榜”可点击标签，也不绘制没有字段支持的真人头像/昵称。
- 单条“最新记录”高亮属于后续可选视觉状态，需要接入方明确记录标识；不假设当前已有“我的全球名次”。

交付：空榜、单条、完整 20 条、超长文案四态；前三名奖牌、职业徽章、列表行标注。

### 4.5 结算、暂停及其他系统页

- 胜利：剩余小队与旗帜为主视觉，星级和真实战绩依次出现，主操作清晰。
- 失败：用损坏徽章和小队撤退姿态表达，保留重试/现有复活入口，避免大面积刺眼红闪。
- 暂停：清晰的继续按钮与现有次级操作，不在这里增加新玩法。
- 成长、科技、挑战、任务等现有页面复用同一面板/列表/标签组件，避免每页重新定义一套配色和卡片。

## 5. 怪物与 Boss

### 5.1 七种普通/精英怪物

| 现有类型 | 轮廓主特征 | 外观与动作设计 | 手机辨识目标 |
|---|---|---|---|
| normal | 大头、破衣、左右不齐肩线 | 苔绿皮肤、低频衣褶、拖步 | 与蓝色士兵轮廓和明度分开 |
| fast | 细腿、前倾背、长前臂 | 黄绿点缀、短促跑步姿态 | 遮掉颜色也能识别速度型 |
| shield | 宽盾占据前侧 | 钝角金属盾、厚甲边缘、较重步态 | 盾牌是第一阅读点，不被头饰抢走 |
| split | 双囊/不对称背部体块 | 紫色囊体、分裂时出现两组小残影 | 分裂来自身体特征，避免只靠紫色 |
| spitter | 胀腮/大口器、弓背 | 酸绿口部、吐酸前口器亮起 | 预备动作与普通行走区分 |
| elite | 宽肩、巨拳、厚胸甲 | 深绿灰主体、局部危险纹样 | 体型和手部识别，不无限加特效 |
| bomber | 圆腹、突出容器/危险标识 | 橙红局部、爆裂提示纹样 | 当前复用 fast 外形，设计独立概念；独立模型加载需交接程序方 |

产出每种怪物的正/侧/背视图、战斗镜头小尺寸剪影、材质色卡、行走/受击/死亡关键姿态。死亡表现采用卡通倒地和碎光，不做血肉细节。

### 5.2 现有 Boss 家族

| 现有模型风格 | 视觉识别点 | 演出重点 |
|---|---|---|
| bruiser | 单侧巨拳、厚重头肩 | 拳部蓄力与地面冲击 |
| bulwark | 大盾与半圆防护结构 | 护盾外缘轮廓、破盾碎片 |
| hivelord | 背部巢囊与召唤组织 | 巢囊脉动、召唤位置提示 |
| spitking | 巨口与酸液罐状腹部 | 口器预热、酸液落点 |
| titan | 厚甲、机械拳和低重心 | 关节动作、沉重落地，甲片不要遮满身体 |
| overlord | 核心胸腔与冠状肩部 | 随现有阶段改变局部亮区和核心表现 |

模型家族不等于每个当前关卡都有该 Boss。关卡与技能对应按当前配置交付，不新增攻击阶段、护盾规则或召唤数量。

背景概念稿可以包含氛围光，但运行时素材应分清底色、贴图和可由接入方播放的效果，避免把光照和警示圈烘焙为永久贴图。洞穴场景以洞顶/雾层代替露天天空，不生硬贴一张蓝天。

|---|---|---|

| 散弹枪 shotgun | 短粗枪管、宽前握把 | 较宽枪焰、离散弹丸、簇状命中；不凭视觉新增弹丸 |
| 狙击枪 sniper | 长枪管、清晰瞄具、细长轮廓 | 小而亮的枪口、窄亮芯轨迹、集中命中环 |
| 机枪 mg | 方形机匣、箱式弹仓、加固枪托 | 连续短闪、短促弹道；不让枪焰合成一块白面 |

| 火箭炮 rocket | 粗筒、导流尾部、明显肩托 | 小型尾焰、烟迹、由内向外的爆炸环；半径跟随已有真实命中范围 |

| 电磁枪 tesla | 双叉枪口、线圈和局部电极 | 紫白细电弧、节点火花；只连接真实命中的目标 |

已有八条进化沿用对应枪族：双管步枪、散弹风暴、幻影狙击、风暴机枪、炼狱喷射、地狱火箭、极寒穿透炮、雷霆链式炮。以结构升级和局部能量件区分，不改变武器手持朝向、枪口位置和攻击规则。

### 7.1 特效时序与优先级

下列为视觉时长设计目标，不用于改变伤害结算时间、模拟时间或真实死亡时点。

| 事件 | 设计目标 | 限制 |
|---|---|---|
| 枪口闪光 | 40–70ms，小面积亮芯 | 必须贴合枪口，不覆盖士兵头部 |
| 普通命中 | 80–140ms，局部火花与材质闪亮 | 不触发全屏闪白或全屏震动 |
| 暴击/精英命中 | 120–200ms，轮廓更明确的局部冲击 | 保留门标签和敌人轮廓 |
| 普通死亡 | 约 350–500ms 的倒地/碎光分镜 | 只画死亡动画，不延迟真实击杀或人为加无敌 |
| 补兵 | 来源数值通知 + 一次足底扩散圈 | 沿用实际增量和高频合并规则 |
| Boss 死亡 | 600–900ms，核心熄灭和局部爆散 | 不遮盖结算主按钮，接入方确认既有流程 |

敌人攻击预警在所有特效之上保持可读；普通弹道不能画成敌人的危险红色。提出低特效密度稿时，只减少装饰密度，保留收益、危险和命中信息。不要求增加震屏、hit-stop、时停或更改击退数值。

页面稿导出 PNG 并附可编辑源文件；简单 UI 图标优先 SVG，另附 1×/2× PNG，图片不得烘焙可变分数、武器等级、按钮文案或排行榜名字。

怪物/武器的概念画只是建模参考。可交付模型需另有 DCC 源文件、GLB、贴图、尺寸/轴向/挂点说明及 LOD。现有怪物五部件为 `Body/Head/Arms/LegL/LegR`；新模型需维持接入方要求的命名和共用材质。不能把新增骨骼动画、独立武器加载或新着色器暗藏在美术交付里。

2D 道具图标建议 256×256 透明母版，展示卡片可用 512×512；页面稿 390×844 与 2×导出分开标注。贴图尺寸、面数、透明层数和压缩格式由接入方根据现有移动端预算确认，默认不高于同类现有资产成本。

每项资产登记：编号、用途、版本、源文件、导出文件、视角、尺寸/单位、锚点、透明要求、主题/颜色、制作来源与许可、审核状态。工作状态统一为“待设计 → 设计稿待确认 → 待制作 → 资产待验收 → 已交接 → 游戏内验证通过”。本轮停留在设计方案阶段。

## 9. 验收与优先级

**P0：**先统一战斗关键视觉、HUD、门标签、补兵通知和三种基础怪物，解决“看不清发生了什么”。

**P1：**首页、军械库、三把基础枪械、基础攻击特效与本机战绩榜。

**P2：**其余怪物/Boss、完整武器进化、十关主题资产和系统页统一。

每批验收必须包括：

1. 390×844 原尺寸对照，不放大图片来掩盖小尺寸识别问题；360×640 和 430×932 复核。
2. 灰度剪影能分清友军、盾怪、快怪和精英；背景不会吞掉脚部与武器轮廓。
3. 三扇门的文字、补兵消息和 Boss 预警同时出现时仍可读，不以看不见的按钮区域代替实际触控检查。
4. 八类枪械在相同角度下可区分；枪口闪光贴合枪口；装饰范围不误导攻击判定。
5. 战绩榜不虚构联网、玩家数据、奖励或名次；少量记录和空榜布局成立。
6. 每张透明图有真实 alpha，无棋盘格假透明或白边；来源许可记录齐全。
7. 接入方提供游戏内截图及同设备、同场景的性能对比；只有通过该步骤，资产状态才能从“已交接”改为“游戏内验证通过”。设计文件本身不能证明运行帧率。

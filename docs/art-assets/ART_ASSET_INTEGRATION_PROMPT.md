# 《膨胀小队》美术资产包导入、优化与游戏集成总任务

> 目标仓库：shellFan/h5-  
> 来源资产包：用户提供的《膨胀小队》H5全套美术资产库.zip  
> 目标：把概念素材转化为可维护、可加载、适配 H5 与微信小游戏的正式游戏资源，并完成实际集成与验收。

## 0. 最高优先级规则

1. 先审查仓库现状、引擎、渲染管线、现有资源目录、资源加载器、构建脚本、运行测试和最近提交。不要假设项目使用某个引擎。
2. 先建立独立分支开展工作；不得直接覆盖 master，不得重写历史，不得强推。
3. 保留核心玩法、三跑道、自动射击、增益门、士兵成长、金币经济、关卡和 Boss 逻辑。此次任务以美术升级和资源接入为主，不擅自改玩法数值。
4. 不得把整张概念截图、素材表或拼图直接当作正式游戏 Sprite 使用。
5. 不得把 JPG 冒充透明 PNG、把 2D 概念图冒充 GLB 模型、把静态图冒充骨骼动画。
6. 不得生成随机网络图片或使用未核验的外链资源。
7. 每项资源必须经过实际检查，确认路径、格式、尺寸、透明通道、引用和加载结果。
8. 任何不确定的资源用途先登记为待确认，不要猜测后直接替换线上素材。
9. 所有修改必须可回滚；先保留旧资源，再逐步切换引用。
10. 不得仅输出报告，必须完成能安全完成的代码、资源、测试和文档工作。

## 1. 已知输入资产包事实

初步审计结果：
- 共 90 个文件，全部为 JPEG。
- 总解压体积约 63.7 MB。
- 59 张为 1024×1024。
- 29 张为 768×1376。
- 2 张为 1376×768。
- 发现 5 个文件内容完全相同的重复图。
- 当前资产包没有原生透明 PNG。
- 资产包含 UI 图集、图标图集、枪械设计图、怪物/士兵概念图、Boss 设计图、战斗场景截图、地图背景和环境道具图。

因此，不能将 90 张 JPG 全部直接复制到运行时资源目录。必须先去重、分类、拆分、检查、转换和建立资源映射。

## 2. 美术方向锁定

以用户提供的《膨胀小队》战斗截图为风格基准：
- 高品质 3D 卡通玩具战争风。
- 绿色玩具士兵：军用头盔、战术背包、绿色护甲、清晰枪械轮廓。
- 怪物：紫色、红色、橙色等高辨识度卡通怪物。
- Boss：大型机械装甲、夸张轮廓、明确体型差异。
- 场景：阳光军事基地、混凝土三跑道、草地、沙袋、木箱、坦克残骸、瞭望塔、铁丝网。
- 增益门：绿色人数、蓝色火力、金色金币。
- UI：明亮、圆润、立体、清晰，适配竖屏小屏幕。
- 禁止回退到蓝紫色赛博朋克走廊风格。
- 全部新资源必须统一材质、比例、镜头、光照、描边和色彩体系。

## 3. 第一步：仓库与输入审计

执行：
- 确认当前分支、工作区是否干净、HEAD SHA。
- 找出实际游戏入口、资源加载入口、场景文件、UI 实现、角色/怪物/武器渲染代码。
- 找出现有士兵 GLB、骨骼、动画、材质和贴图，优先复用。
- 检查现有资源尺寸、格式、引用、重复文件和未使用资源。
- 解压用户放入仓库根目录或指定路径的资产 ZIP；如果文件不存在，明确报告缺少输入路径，不要假装已导入。
- 生成资产清单 CSV/JSON/Markdown，记录原始文件名、哈希、尺寸、格式、大小、分类、处理状态、目标路径、引用状态。

## 4. 第二步：资源清洗与标准化

建议目录以项目现有规范为准；若无统一规范，可采用：
- assets/art-source/：保留原始输入和审计记录，不进入运行时加载。
- assets/game/characters/soldiers/
- assets/game/characters/monsters/
- assets/game/characters/bosses/
- assets/game/weapons/
- assets/game/maps/backgrounds/
- assets/game/maps/terrain/
- assets/game/maps/props/
- assets/game/gates/
- assets/game/effects/
- assets/game/ui/
- assets/game/icons/
- assets/game/marketing/

处理要求：
1. 按 SHA-256 去重，重复原图只保留一份，并在清单记录来源文件名。
2. 原始文件只读保留，不覆盖原图。
3. 统一文件名为小写英文 snake_case，名称表达实际用途。
4. 根据实际内容拆分图集；拆分必须人工/视觉复核，不允许凭固定网格盲切导致切掉边缘或混入相邻元素。
5. 所有需要透明的元素，先抠图并检查边缘光晕、锯齿、半透明边缘和背景残留；JPG 不可直接声明为透明素材。
6. 图集切片后，记录 frame 尺寸、pivot、padding、atlas 元数据。
7. UI 文字、关卡数字、金币数、按钮文案优先由程序绘制，不使用 AI 烧录的乱码文字。
8. 对地图背景、战斗截图和宣传图明确标记为 background/concept/marketing，不得误用作角色精灵。
9. 转 WebP/PNG 前比较视觉质量和文件体积；有透明通道用 PNG/WebP alpha，无透明需求优先 WebP/JPEG。
10. 不要为了格式统一而无意义地增加包体。

## 5. 第三步：正式游戏资源制作与替代策略

按以下优先级处理：

### A. 立即可落地
- Logo、头像、徽章、商店/排行榜装饰、独立 UI 面板、按钮底板、图标。
- 可拆分的背景、道路贴图、环境道具。
- 金币、枪口火焰、爆炸、升级光效等可拆分特效。

### B. 需要加工后落地
- 怪物概念图：抠图、统一朝向、尺寸、锚点，制作静态展示或 billboard 版本；若当前游戏要求 3D 动画，则继续建模/绑定，不得直接假装完成。
- 士兵设计图：优先沿用项目现有 GLB 骨骼模型，把新设计作为材质、贴图、颜色和配件升级参考；如果概念图与现有模型不匹配，先做适配验证。
- 武器设计图：提取独立武器图标；真实 3D 武器需要单独建模或复用已有模型。
- 地图概念图：拆分背景/中景/前景与地面模块，确保滚动循环时无明显接缝。

### C. 不可由静态图片替代
- GLB/FBX 网格模型、骨骼、蒙皮、动画、碰撞体、实时粒子系统。
- 对这些项目建立缺口清单，使用现有模型/程序化方案或后续建模流程补齐。

## 6. 第四步：UI 全面升级

基于项目真实页面逐一升级，不只制作静态稿：
- 主菜单、玩家信息、等级经验、金币/钻石。
- 战斗 HUD、关卡进度、Boss 血条、士兵人数、暂停。
- 三个增益门：人数/火力/金币，颜色和图标一眼可辨。
- 士兵升级、武器升级、成长属性。
- 商店、任务、签到、成就、排行榜。
- 胜利、失败、结算、奖励翻倍、下一关、重试。
- 设置、新手引导、加载页。

适配规则：
- 以真实安全区、刘海屏、底部手势区域为准。
- 至少覆盖 320、360、375、390、414、430 CSS px 宽度。
- 所有点击区域满足移动端可操作尺寸。
- 文本不溢出、不遮挡战斗关键区域。
- 竖屏优先；横屏按项目现有策略处理。
- 不得把完整 UI 截图作为一张背景图来伪装交互界面。

## 7. 第五步：战斗美术升级

- 士兵队列要有层次，人数多时不能完全重叠成一团。
- 士兵移动、转向、射击、受击与死亡动画必须保持现有逻辑正确。
- 怪物轮廓要清晰，颜色不能与背景混淆。
- Boss 体型、血条和攻击反馈明显。
- 三条跑道边界清楚，增益门位置稳定，穿越反馈明确。
- 子弹、激光、枪口火焰和命中特效不能遮挡关键 UI。
- 爆炸和粒子要有生命周期、数量上限和对象复用。
- 不得因美术升级造成怪物刷新、移动、攻击、碰撞或难度曲线异常。

## 8. 第六步：性能与包体

目标是移动端优先：
- 建立资源尺寸预算和单关加载预算。
- 大图按需加载，非当前关卡资源延迟加载。
- 复用纹理、材质、Sprite Atlas 和粒子对象。
- 避免每帧创建纹理/材质/几何体。
- 控制透明叠层、粒子数量、阴影和后处理。
- 纹理尺寸按实际显示大小设定，禁止所有资源统一放大到 4K。
- WebP/PNG 压缩后逐张抽检。
- 检查内存释放、场景切换和重复进入关卡。
- 记录升级前后首屏时间、资源总大小、内存、FPS、Draw Calls（引擎支持时）。

## 9. 第七步：测试与视觉验收

必须真实运行，不可只通过静态代码检查：
1. 安装依赖并运行项目规定的检查。
2. 构建 H5。
3. 运行完整战斗流程。
4. 测试三跑道和三种增益门。
5. 测试士兵数量较少、中等、大量时的显示。
6. 测试普通怪物、精英和 Boss。
7. 测试武器升级、金币奖励、胜利、失败、重试。
8. 测试排行榜、商店和成长 UI。
9. 测试不同手机宽度、刘海屏和底部安全区。
10. 检查图片 404、路径大小写、透明边缘、模糊、拉伸、错位、闪烁。
11. 检查长时间运行的 FPS、内存增长和卡顿。
12. 输出改造前后截图和测试结果。

- 现有玩法回归通过。
- 手机适配通过。
